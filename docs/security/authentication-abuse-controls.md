# Authentication-abuse controls

## Current application controls

| Control | Sentinel configuration / behaviour |
|---|---|
| Password length | Minimum 12 characters |
| Composition | No arbitrary uppercase/lowercase/digit/symbol requirement; long passphrases are supported |
| Weak-password screening | Offline common-password deny-list is loaded at startup and applies to create, reset and change-password flows |
| Failed sign-in lockout | Five failed attempts lock the account for 15 minutes; login failures use a generic response |
| Password reset | Anonymous reset and completion endpoints are rate-limited; reset tokens are generated by ASP.NET Identity |
| Two-factor authentication | Voluntary, per-user TOTP authenticator-app enrolment. Sentinel enables it only after the user verifies a current six-digit code. |
| Authenticator QR code | Generated locally from the signed-in user's Identity authenticator key. Sentinel does not send the setup URI, key or QR image to a third-party QR service. |
| Recovery codes | A fresh set of single-use recovery codes is shown once after enrolment or regeneration. Users must store them securely; Sentinel does not retain a readable copy. |
| Session invalidation | Security-stamp validation is configured on every authenticated request so disable, lock and access changes invalidate existing sessions |
| Browser cookies | Sentinel-owned cookies are host-only, HTTPS-only, HttpOnly and SameSite=Lax |
| Global request budget | 150 requests/minute per authenticated user or source address, with more restrictive policies for sensitive workflows |

Current values are implemented in `Sentinel/Program.cs`. Any change must update this document and be regression-tested.

## Voluntary authenticator-app two-factor authentication

Two-factor authentication is deliberately optional for the current beta. It is
not an organisation-wide enforcement setting and does not change another
user's account. A signed-in user enrols from **User menu → Two-Factor
Authentication**:

1. Select **Set up an authenticator app**.
2. Scan the locally generated QR code in a TOTP-compatible authenticator app,
   or enter the displayed setup key manually.
3. Enter the six-digit code generated by the app. Sentinel enables two-factor
   authentication only after this verification succeeds.
4. Save the displayed recovery codes in an approved secure location. They are
   presented only once and each can be used once.

An enrolled user can require a fresh code for their current browser, generate a
replacement recovery-code set, reset their authenticator app, or disable
two-factor authentication from the same page. Resetting an authenticator
requires enrolling again and produces a new recovery-code set.

The setup key, QR image and recovery codes are sensitive account data. The
related pages are authenticated, use no-store response caching, and must never
be added to diagnostic logs, telemetry, browser storage or support tickets.

## Rate-limit policies

| Policy | Budget | Intended use |
|---|---:|---|
| `sensitive-data` | 30/minute | Sensitive patient/case data access |
| `bulk-export` | 10/hour | High-volume export workflows |
| `bulk-export-moderate` | 20/hour | Moderate export workflows |
| `workflow-api` | 100/minute | Standard workflow API actions |
| `workflow-api-moderate` | 60/minute | Higher-impact workflow actions |
| `lookup-api` | 200/minute | Reference-data lookups |
| `password-reset` | 5/15 minutes per source address | Anonymous reset completion |
| Password-reset request policy | 5/15 minutes per user/source | Reset-request flow |

## Operational response

1. Treat repeated failed login, reset and rate-limit events as a potential abuse signal.
2. Review the affected account, source address and correlated application/security logs without exporting patient data.
3. Unlock an account only after confirming the legitimate user through the organisation's help-desk process.
4. Do not disclose whether an email/account exists, is disabled or is locked in a public response.
5. If abuse is sustained, use infrastructure controls (firewall/WAF/reverse-proxy rate limits) in addition to Sentinel's application limits.

## Required retests

- Five invalid sign-ins: verify generic responses and temporary lockout.
- Valid sign-in after expiry or administrator unlock.
- Password manager paste and a 12+ character lowercase passphrase.
- A password known to be on the deny-list for create, reset and change flows.
- Reset-token reuse and expiry.
- Two sessions: disable/lock the user, then refresh both protected requests and verify denial.
- Enrol a test user using an authenticator app; verify that a current TOTP code
  completes enrolment and that sign-in then requires a second-factor code.
- Verify an incorrect enrolment code does not enable two-factor authentication.
- Verify recovery codes are displayed once, work once, and are invalid after
  replacement, authenticator reset or two-factor disablement.

## Regression evidence — 17 September 2026

The following checks were completed against the local development instance using the synthetic account `session-invalidation.test.20260818@sentinel.invalid`:

| Check | Result | Evidence |
|---|---|---|
| Five invalid sign-ins | Pass | Each attempt returned the same generic sign-in failure message; the account was locked for 15 minutes after the fifth attempt. |
| Administrator unlock and valid sign-in | Pass | The account was unlocked from User Management and could sign in normally. |
| Password paste | Pass | The synthetic account could sign in after the password was pasted into the login form. |
| Lowercase passphrase | Pass | A new confirmed synthetic account was created, changed and used to sign in with an 18-character lowercase-only passphrase. |
| Common-password rejection (live) | Pass | The authenticated change-password flow rejected the deny-listed `password1234!` value with the expected common-password validation error. |
| Disabled-account sign-in | Pass | A disabled account received only the same generic sign-in failure response; after re-enabling it, sign-in succeeded. |
| Existing-session invalidation | Pass | The synthetic account was signed in through two independent browser sessions. After an administrator disabled it, refreshing either Dashboard session redirected it to the sign-in page. The account was then re-enabled. |
| Reset-token reuse | Pass | A reset token completed one reset successfully. Reopening the same link displayed the reset form, but submitting it after the rate-limit window returned: “The password reset link is invalid or has expired. Please request a new one.” |
| Reset-token expiry | Pass (automated) | `PasswordResetExpiryTests` uses ASP.NET Identity's real reset-token provider with ephemeral keys and a two-second, test-only lifetime. A fresh token changes the password once; reuse and expiry are rejected, leave the password and security stamp unchanged, and return the generic invalid-or-expired response. The production default remains 24 hours. |
| Common-password deny-list | Pass (automated) | `CommonPasswordValidatorTests` verified case-insensitive rejection and the 3,000-entry list requirement. |
| Reset-token URL encoding | Pass (automated) | `PasswordResetTokenEncodingTests` verified token encoding/decoding round trips. |

The reset-token expiry check runs in an isolated fixture only; it does not shorten Sentinel's production token lifetime.
